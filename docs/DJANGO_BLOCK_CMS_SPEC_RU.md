# ТЗ: отдельный Django-проект для сайта MangaLaunch

Дата: 28 октября 2026 года. Статус: ревью и техническое задание, реализация не начата.

## 1. Результат и принятые решения

Перенести текущий статичный лендинг в самостоятельный Django-проект. Редактор собирает одну или несколько страниц из типизированных блоков, меняет их порядок и содержимое через административный интерфейс. Блоки представлены настоящими дочерними моделями `django-polymorphic`.

Обязательна многоязычность. Начальные языки — русский и английский; добавление следующего языка не требует изменения схемы моделей. Переводятся страницы, блоки, навигация, SEO и все подписи интерактивных макетов.

Изменения применяются сразу после успешного сохранения. Предпросмотр, черновики, согласование и отдельная публикация не предусматриваются. Незавершённая форма в браузере ничего на сайте не меняет. Сохранение одного действия редактора выполняется атомарно: посетитель видит состояние до операции или после неё.

Текущий `frontend` служит визуальным и функциональным эталоном. В рамках этого документа файлы лендинга и серверное приложение не переделываются.

## 2. Ревью текущего лендинга

Исходные файлы: `frontend/index.html`, `frontend/styles.css`, `frontend/main.js`, `frontend/assets/`.

| Часть | Сейчас | Что требуется при переносе |
| --- | --- | --- |
| Разметка | Один HTML-файл с семью основными секциями | Базовый шаблон страницы и отдельный шаблон каждого типа блока |
| Контент | Тексты, изображения, кнопки и метаданные записаны в HTML | Поля моделей и формы редактирования |
| Оформление | Общие CSS-переменные, адаптивная верстка, анимации | Сохранить внешний вид; вынести общие стили и стили блоков в читаемые исходные файлы |
| Макет библиотеки | Книги и коллекции заданы разметкой | Управляемые демонстрационные книги, коллекции и подписи |
| Макет читалки | Один экземпляр; фразы и часть подписей записаны в JS | Данные текущего языка из моделей; независимое состояние каждого экземпляра |
| Сборка страницы | Фиксированный порядок секций | Добавление, удаление, скрытие и перестановка блоков |
| Навигация | Фиксированные якоря `#library`, `#reader` и другие | Управляемые ссылки и проверка их целей для каждой локализации |
| Скачивание | Ссылок пока нет, отображается честное уведомление | Сохранить это состояние, пока редактор не добавит реальные ссылки |

Перенос хорошо подходит для серверного рендеринга Django: страница не зависит от внешних API и клиентского приложения. Текущие стили, иллюстрацию, логотип, SVG и большую часть интерактивного поведения можно сохранить.

Просто разделить HTML на `{% include %}` недостаточно. В `main.js` есть обращения к единственному `.reader-demo`, `#library-books`, `#extension-steps` и глобальный поиск переключателей. Если редактор удалит нужную секцию или добавит второй такой блок, текущая инициализация может завершиться ошибкой либо связать разные экземпляры между собой. Это необходимо исправить при реализации.

Новый проект получает цену эксплуатации: база данных, административные учётные записи, резервное копирование и обновления зависимостей. Это оправдано управляемым контентом и несколькими страницами, но само по себе не ускоряет текущий статичный сайт. Это архитектурная оценка по локальному коду, без нагрузочных измерений.

## 3. Роль django-polymorphic

`PolymorphicModel` позволяет получить через базовый queryset экземпляры конкретных дочерних моделей. Для разных типов блоков это подходящий механизм. Поля Hero, FAQ и читалки находятся в соответствующих моделях, а общий список сохраняет порядок. Основа — стандартное наследование Django с отдельными таблицами. Источники: [django-polymorphic](https://github.com/django-commons/django-polymorphic), [наследование моделей Django](https://docs.djangoproject.com/en/5.2/topics/db/models/#multi-table-inheritance).

Библиотека предоставляет классы для полиморфной админки и inline-форм. Готового конструктора страниц с нужным дизайном и перетаскиванием это не даёт: редактор порядка и связь страницы с блоками реализуются в проекте. Источник: [Admin Integration](https://django-polymorphic.readthedocs.io/en/stable/admin.html).

Не хранить все виды блоков в одной таблице с десятками необязательных полей и `kind`, а также не складывать редактируемый контент целиком в произвольный JSON. Тип определяется реальной дочерней моделью; набор разрешённых типов задаётся в коде.

## 4. Техническая основа

- Самостоятельный проект и собственная база данных; отдельный каталог и имя репозитория определяются при реализации.
- Python 3.13, Django 5.2 LTS и совместимый выпуск `django-polymorphic`. Перед началом реализации проверить матрицу совместимости и закрепить точные поддерживаемые патчи в lock-файле. Выбор LTS опирается на [таблицу поддержки Django](https://www.djangoproject.com/download/).
- PostgreSQL в рабочем окружении. SQLite допустим для простого локального запуска, но тесты ограничений и конкурентных изменений также выполняются на PostgreSQL.
- Django Templates, обычные CSS и JavaScript. Сервер отдаёт готовый HTML; отдельный SPA и публичный API конструктора для первой версии не требуются.
- Django admin с расширением для типов блоков. Небольшой JS для перестановки блоков; все основные действия доступны и без перетаскивания.
- Django i18n для интерфейса, локализованные записи моделей для содержимого сайта.
- Кеш через стандартный интерфейс Django; общий Redis для рабочего окружения с несколькими процессами. Без кеша сайт сохраняет корректность.
- Изображения и загружаемые файлы хранятся отдельно от исходников; встроенные иллюстрации и доверенные SVG входят в статические ресурсы проекта.

Предлагаемые приложения: `pages` — страницы и маршрутизация, `blocks` — типы и рендеринг блоков, `site_settings` — оформление и навигация, `media_assets` — файлы. Сервисы загрузки страницы, сохранения и перестановки должны иметь одного владельца, без дублирования между admin и views.

## 5. Модель многоязычного контента

### 5.1. Страницы

`Page` — языконезависимая сущность страницы:

- `id`: UUID;
- `internal_name`: понятное редактору название;
- `key`: уникальный стабильный ключ, например `home`, `windows`, `features`;
- даты создания и изменения.

`PageTranslation` — содержимое и адрес страницы в одном языке:

- `page`: FK на `Page`, удаление страницы удаляет её переводы;
- `language_code`: код из разрешённого списка языков;
- `path`: нормализованный путь без языкового префикса; пустое значение означает главную страницу языка;
- `title`, `meta_title`, `meta_description`, изображение для социальных сетей и его альтернативный текст;
- `is_visible`: обычный флаг доступности страницы;
- `content_version`: увеличиваемый счётчик для кеша и защиты от потери изменений;
- даты изменения и редактор последнего изменения.

Ограничения: один перевод страницы на язык; уникальный `(language_code, path)`; существующие и новые пути проверяются на конфликты с административными и служебными маршрутами. Код языка хранится в одном нормализованном формате, согласованном с `LANGUAGES` Django.

Флаг видимости не вводит статусов согласования. У видимой страницы каждое сохранение сразу меняет сайт. У скрытой страницы маршрут возвращает 404, пока редактор не включит видимость.

### 5.2. Блоки

`PageBlock(PolymorphicModel)` — конкретная базовая модель с полями:

- `id`: UUID;
- `page_translation`: FK на `PageTranslation`, `on_delete=CASCADE`;
- `position`: порядок внутри перевода страницы;
- `internal_name`: название в административном списке;
- `anchor`: необязательный уникальный якорь внутри этого перевода;
- `is_enabled`: показывать ли блок;
- `tone`: вариант из фиксированного списка, например `paper`, `sage`, `dark`;
- даты изменения.

Ограничения: уникальные позиции, уникальные непустые якоря в пределах перевода. На публичной странице учитываются включённые блоки и явно заданный порядок. Вложенность блоков в первой версии не требуется.

Один экземпляр блока принадлежит ровно одному переводу страницы. Содержимое разных языков не связано общими изменяемыми текстовыми записями. При копировании блока создаётся полный независимый экземпляр с дочерними строками и новым ID; ссылки на файлы могут переиспользоваться.

Нет необходимости делать полиморфными FAQ-строки, кнопки и книги. Для них используются обычные дочерние модели с FK на конкретный тип блока и своим `position`.

### 5.3. Языковые правила

1. Начальные языки: `ru` и `en`; русский — язык по умолчанию. Список языков задаётся централизованно, а не отдельными полями `title_ru`, `title_en`.
2. Структура страниц в разных языках может отличаться: порядок, количество блоков и CTA задаются для каждого `PageTranslation`.
3. Тексты блоков хранятся как контент соответствующего языка. `gettext` используется для служебных подписей шаблонов и административного интерфейса, а не для перевода записей БД.
4. Переводятся также меню, footer, alt-тексты, кнопки, подсказки, ARIA-метки, уведомление об отсутствии ссылок, названия коллекций, подписи страниц и все фразы демонстрационной читалки.
5. Интерфейс редактора и язык редактируемого контента — разные настройки. Редактор с русским admin может менять английскую страницу.
6. Отсутствующий или скрытый перевод не подменяется русским текстом по английскому URL: ответ 404. Переключатель языка показывает только доступные переводы этой же `Page`.
7. Автоматический перевод и обращения к платным сервисам перевода не входят в первую версию.
8. Числа и даты форматируются в выбранной локали. Время хранится с часовым поясом; язык документа устанавливается через `<html lang="…">`.
9. Изменение английского содержимого не меняет русское. Общими могут быть только явно общие ресурсы: логотип, файл иллюстрации, идентификаторы платформ.

## 6. Типы блоков и перенос текущих секций

| Текущий участок | Модель | Управляемое содержимое |
| --- | --- | --- |
| `#top` | `HeroBlock` | Надзаголовок, части заголовка с акцентом, описание, иллюстрация, alt, подписи на иллюстрации, платформы, две CTA |
| `#library` | `LibraryShowcaseBlock` | Заголовок и описание секции, преимущества, подпись макета, приветствие, коллекции, демонстрационные книги и прогресс |
| `#reader` | `ReaderShowcaseBlock` | Описание, режимы, кнопка перевода, ограничение платформы, фразы до/после перевода, подписи управления и счётчик |
| `#extensions` | `ExtensionsBlock` | Заголовок, описание, пункты возможностей, текст диаграммы, инструкции подключения |
| Блоки офлайн-чтения и прогресса | `BenefitsBlock` | Упорядоченные карточки с текстами, вариантами иллюстраций, примером загрузок, логотипами трекеров и подписями |
| `#faq` | `FaqBlock` | Заголовок и упорядоченные вопросы с ответами |
| `#download` | `DownloadBlock` | Заголовок, описание, платформы, ссылки, подписи и текст состояния без ссылок |

У одного типа может быть несколько экземпляров на разных страницах и на одной странице. Секция должна работать независимо от наличия остальных типов.

### 6.1. Дополнительные модели

- `FeatureItem`: FK на соответствующий showcase, заголовок, описание, иконка из разрешённого списка, позиция.
- `LibraryCollection` и `DemoBook`: коллекции и карточки макета; принадлежность книги нескольким коллекциям допускается внутри одного блока. Книга содержит название, изображение либо встроенный вариант SVG, подпись, прогресс и необязательную CTA.
- `ReaderPhrase`: FK на `ReaderShowcaseBlock`, позиция, исходная фраза и демонстрационный перевод. Подписи элементов управления и доступности также локализованы.
- `FaqItem`: FK на `FaqBlock`, вопрос, безопасный форматированный ответ, позиция.
- `BenefitItem`: FK на `BenefitsBlock`, тексты и вариант из утверждённых видов карточки.
- `DownloadItem`: FK на `DownloadBlock`, платформа из enum, необязательная HTTPS-ссылка, подпись, дополнительные сведения о версии при наличии, позиция.
- `BlockAction`: FK на базовый `PageBlock`, слот действия, подпись и тип назначения. У каждого типа блока фиксированный набор разрешённых слотов.

Текстовые поля с выделением хранят смысловые части заголовка или ограниченный форматированный текст. Редактор не вводит произвольную HTML-разметку страницы.

### 6.2. Header и footer

`SiteSettings` хранит языконезависимые ресурсы и параметры сайта: название, логотип, favicon, канонический домен, разрешённые языки, основной язык и `version` настроек.

`SiteSettingsTranslation` хранит для конкретного языка подписи меню, footer, юридические ссылки при их появлении, подписи переключателя языка и свою версию содержимого. Дочерние `NavigationItem` упорядочены и имеют локализованную подпись.

Header и footer используются всеми страницами языка. Их сохранение сразу обновляет соответствующие страницы через изменение ключа кеша. Произвольное подключение сторонних скриптов из настроек не предусматривается.

## 7. Контракт ссылок

Типы назначения CTA и навигации:

- страница: FK на `Page`, адрес выбирается в языке текущей страницы;
- якорь: ссылка на включённый блок этого перевода страницы;
- внешний адрес: проверенный `http`/`https`, для скачивания — `https`;
- пустое значение: кнопка не отображается, либо блок показывает специально предусмотренную текстовую заглушку.

Должен быть указан ровно один тип назначения. Запрещены `javascript:`, `data:` и адреса с некорректным форматом. Проверка внешнего адреса не должна автоматически скачивать его содержимое.

При удалении, скрытии или переименовании цели редактор получает понятную ошибку со списком зависимых ссылок. Обновление связанных объектов выполняется одной операцией. Изменение пути страницы не ломает внутренние ссылки, потому что они используют FK; для старого публичного URL создаётся перенаправление. Цепочки и циклы перенаправлений запрещены.

На начальном лендинге внешних ссылок нет. Нельзя добавлять вымышленные ссылки скачивания, контакты, отзывы или статистику.

## 8. Маршрутизация и SEO в нескольких языках

- Все контентные URL имеют префикс языка: `/ru/`, `/en/`, `/ru/windows/`, `/en/windows/`.
- `/` перенаправляет на главную страницу доступного языка: сохранённый выбор пользователя, поддерживаемый `Accept-Language`, затем язык по умолчанию. Ответ перенаправления не кешируется одинаково для разных предпочтений посетителей.
- Адрес открытой страницы определяет язык её контента. Cookie языка не может переключить содержимое `/en/` на русский.
- Переключатель языка ведёт к переводу той же `Page`, даже если его `path` отличается. Если перевода нет, ссылка на него отсутствует.
- На каждой странице собственные `title`, description, canonical и Open Graph. `hreflang` содержит только видимые переводы, включая текущий; `x-default` указывает на доступный вариант по умолчанию, если он существует.
- `sitemap.xml` содержит только доступные страницы. Sitemap и перенаправления обновляются после изменения пути, видимости, добавления или удаления перевода.
- В видимом контенте ровно один H1. Первая Hero-секция может использовать его; дополнительные Hero и остальные секции используют H2. При отсутствии Hero H1 берётся из заголовка страницы.
- Административные и служебные маршруты находятся вне дерева контентных URL.

## 9. Редактор и сохранение

### 9.1. Работа редактора

В списке страниц видны внутреннее название, языки, пути, видимость и время изменения. В карточке страницы доступны переводы. В карточке перевода — SEO и упорядоченный список блоков с типом, названием, видимостью и действиями.

Действия над блоком: добавить с выбором типа, открыть форму конкретного типа, копировать, переместить выше/ниже, перетащить, включить/выключить, удалить с подтверждением. В форме конкретного блока редактируются его обычные дочерние строки. Глубоко вложенный универсальный конструктор форм не требуется.

Использовать `PolymorphicParentModelAdmin`/`PolymorphicChildModelAdmin` и при необходимости полиморфные inline-классы. Не выдавать их наличие за готовый drag-and-drop-интерфейс. Перестановка работает также клавиатурой и кнопками.

Смена типа существующего блока не является изменением поля. Для первой версии редактор создаёт новый блок нужного типа и удаляет старый: так не теряются и не остаются скрытыми поля дочерней таблицы.

### 9.2. Правила изменения данных

1. Сохранение блока и всех изменённых дочерних строк происходит в одной транзакции. Ошибки показываются у полей и ничего частично не применяют.
2. Счётчик версии затронутого перевода увеличивается в той же транзакции, что и содержимое. Очистка или прогрев кеша выполняются только после commit; следующий запрос использует актуальный ключ. Валидация выполняется и сервисами, и формами, ограничения целостности дополнительно закрепляются в БД.
3. Изменение общих настроек обновляет их версию. Перенос объекта между владельцами, если он появится позднее, обязан затронуть обе зависимости кеша.
4. Перестановка блоков атомарна: блокировка родительской записи, проверка ожидаемой версии и безопасное обновление уникальных позиций без промежуточных конфликтов.
5. Одновременное редактирование не должно молча затирать чужие изменения. При несовпадении `content_version` сохранение отклоняется с предложением обновить форму.
6. Все изменения редакторов фиксируются штатным журналом действий Django admin. История редакций и восстановление старых версий не входят в первую версию; `content_version` — технический счётчик, а не хранилище редакций.
7. Нет отдельного состояния или действия «опубликовать», а также маршрута рендеринга несохранённой формы.

Роли: редактор контента, администратор пользователей и настроек. Посетители не имеют прав редактирования. Ограничение редакторов по языкам можно добавить позже; обычные разрешения Django обязательны сразу.

## 10. Рендеринг и JavaScript

На запрос страницы сервер загружает её перевод, общие настройки языка и включённые блоки. Реестр в коде сопоставляет класс модели с шаблоном и загрузчиком связанных данных. Путь шаблона, Python-класс и исполняемый код не берутся из редактируемых строк БД.

Каждый блок имеет корневой элемент с `data-block-type` и уникальным ID. Весь JS макета ищет элементы внутри этого корня. Инициализация происходит для всех найденных экземпляров соответствующего типа. Отсутствующий блок не запускает свой обработчик.

Обязательные изменения текущего JS:

- `initLibrary(root)`, `initReader(root)`, `initExtensions(root)` со своим состоянием;
- уникальные ID для tabpanel, ARIA-связей, диапазонов и инструкций; фиксированные `#library-books` и `#extension-steps` не дублируются;
- режим, текущая страница и перевод одного макета не влияют на второй;
- локализованные фразы, подписи и данные приходят безопасно через `json_script` или эквивалентное экранированное представление, без конкатенации CMS-текста в JavaScript;
- наличие и порядок секций не предполагаются заранее;
- обработчики и наблюдатели не устанавливаются многократно на один элемент;
- содержимое доступно при отключённом JS: библиотека показывает начальную коллекцию, FAQ использует нативный `details`, навигация и текст видимы;
- `prefers-reduced-motion`, управление с клавиатуры и видимый фокус сохраняются.

Интерактивные макеты остаются иллюстрацией возможностей приложения. Они не выполняют запросы к источникам, трекерам, GitHub или переводчикам. Отдельная работающая читалка на сайте не требуется.

## 11. Производительность и кеш

Полиморфная загрузка не означает один SQL-запрос на всю страницу. Для небольшой выборки библиотека выполняет базовый запрос и дополнительные запросы для встретившихся дочерних типов. Ручной вызов `get_real_instance()` для каждого блока создаёт лишние запросы. Источник: [Performance Considerations](https://django-polymorphic.readthedocs.io/en/stable/performance.html).

Требования проекта:

- один загрузчик страницы; пакетная загрузка связанных изображений, CTA, книг и FAQ для каждого типа;
- шаблоны используют подготовленные данные и не создают N+1 при обходе дочерних строк;
- число запросов растёт по числу разных типов и связей, а не линейно по числу одинаковых книг или FAQ;
- кешировать готовый публичный HTML; ключ включает ID перевода, его `content_version`, версии общих настроек и ресурсов шаблона;
- язык всегда участвует в ключе. Содержимое из одного языка не может попасть в другой;
- версия в БД меняется атомарно с данными, включая дочерние записи и удаление; очистка или прогрев кеша выполняются после успешного commit;
- ограничить срок жизни и размер кеша, чтобы старые ключи версий не накапливались бесконечно;
- административные страницы и ответы с пользовательскими сообщениями не попадают в общий публичный кеш;
- не выполнять внешние сетевые запросы в обработчике публичной страницы;
- задать размеры изображений, готовить подходящие варианты для узких экранов, использовать lazy-loading ниже первого экрана;
- кеш не должен быть необходимым условием целостности данных.

Тесты фиксируют отсутствие N+1 при увеличении числа одинаковых блоков и строк. Обещание конкретного FPS или времени ответа без измерений в ТЗ не закладывается.

## 12. Файлы и безопасность

- CSRF, безопасные административные сессии, HTTPS рабочего окружения, `DEBUG=False`, секреты из окружения, ограниченный `ALLOWED_HOSTS`.
- Обычные CMS-строки экранируются шаблонами. Форматированный текст проходит разрешающий фильтр тегов и атрибутов; произвольный JS, CSS и iframe не принимаются.
- Загружаемые изображения проверяются по фактическому содержимому, размерам и весу. Допустимые форматы и пределы задаются явно. В первой версии достаточно PNG, JPEG и WebP; доверенные встроенные SVG хранятся в коде.
- Файлы, используемые страницами, нельзя незаметно удалить. Админка показывает зависимости; операция запрещается либо предлагает безопасную замену.
- При замене изображения используется новое имя/версия ресурса. Старый HTML-кеш не должен показывать сломанный URL.
- Внешние медиа не скачиваются сервером только потому, что редактор вставил URL.
- Резервные копии охватывают БД и загруженные файлы. Исходники и передаваемый проект не содержат рабочую БД, секреты, пользовательские сессии и личные данные разработчика.

## 13. Начальный контент и перенос дизайна

Начальное наполнение импортируется отдельной идемпотентной management-командой по стабильным ключам. Повторный запуск по умолчанию не перезаписывает уже отредактированные тексты. Режим принудительного обновления, если потребуется, должен быть отдельным явным действием.

Создать русскую главную из текущего лендинга и полноценную английскую локализацию того же содержания. Перевести также мелкие подписи, данные макетов, доступность и SEO. Начальные внешние ссылки скачивания и контакты остаются пустыми в обоих языках.

Сохранить тёплую палитру, композицию первого экрана, типографику, адаптивные состояния, анимации и иллюстрации. Перенос в CMS не должен заменять дизайн типовой административной или шаблонной темой.

Для дополнительной страницы редактор выбирает нужные типы блоков, наполняет их и сохраняет порядок. Добавление второго экземпляра существующего типа не требует доработки шаблона или JS.

## 14. Проверки и критерии приёмки

### Модели и сохранение

- Базовый queryset возвращает настоящие дочерние модели и их поля.
- Удаление и копирование охватывают все дочерние строки; копия имеет независимые ID и тексты.
- Повторные позиции и якоря, конфликтующие маршруты и опасные URL отклоняются.
- Сохранение с ошибкой не меняет ни страницу, ни связанные строки частично.
- Конкурентное сохранение и перестановка не теряют изменения.
- Один успешный Save становится виден на сайте без отдельного действия публикации.
- Изменение/удаление книги, FAQ, CTA, изображения и общих настроек обновляет нужный кеш.

### Многоязычность

- `/ru/` и `/en/` показывают разные сохранённые тексты без смешивания кеша.
- Cookie и `Accept-Language` не меняют язык URL с явным префиксом.
- Изменение русского блока не меняет английский; различающийся порядок блоков разрешён.
- Переключатель сохраняет логическую страницу при разных путях переводов.
- Отсутствующий перевод даёт 404 и не появляется в переключателе и `hreflang`.
- Все интерфейсные подписи макетов, alt, ARIA, SEO и footer имеют перевод; проверка выполняется на настоящем английском начальном контенте.
- Третий язык добавляется настройкой и созданием переводов, без миграции новых `*_xx` полей.

### Страница и взаимодействие

- Эталонная главная визуально сохраняется на ширинах 320, 390, 768, 1024 и 1440 px; нет горизонтального переполнения.
- Работают две библиотеки и две читалки на одной странице, независимо друг от друга.
- Страница работает при удалении reader, library, FAQ или download; console errors отсутствуют.
- Работают меню, клавиатура, FAQ, коллекции, режимы читалки и уменьшение анимации.
- Отсутствие реальных download-ссылок показывает локализованный текст, а не неработающую кнопку.
- Нет лишних запросов к внешним сервисам.

### Безопасность и производительность

- Посетитель не может менять контент, административные действия защищены разрешениями и CSRF.
- CMS-текст не выполняет HTML/JS; опасные файлы и ссылки отклоняются.
- Публичные страницы используют общий кеш без пользовательских данных.
- Тесты SQL подтверждают отсутствие N+1; тесты выполняются и с пустым, и с прогретым кешем.

Проверка реализации: автоматические тесты моделей, сервисов, views и административных форм, браузерные тесты и визуальная проверка. Отдельные сборки приложения к этой задаче не относятся.
